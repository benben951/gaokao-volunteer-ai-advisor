# Tencent Cloud / CloudBase Deployment Postmortem

## 背景

项目最开始在本地和海外平台上可以运行，但手机端在国内访问海外 Vercel 链接不稳定。目标变成：找一个国内能访问、能跑 Express API、能接 DeepSeek、能给一两个人使用的托管方式。

我们尝试了腾讯云相关路线，包括 SCF、CloudBase、云托管等。最终沉淀出一个重要结论：部署不是“平台能不能支持 Express”这么简单，而是要先验证项目形态、入口约定、运行时、费用和公网访问。

## 结果

- 证明了国内平台可以跑这个项目。
- 也暴露出腾讯云 SCF/CloudBase 对入口文件、构建方式、响应头和费用感知的要求比预期更高。
- 后续更推荐先做最小探针，再迁真实项目。
- 如果只是给 1-2 人临时访问，优先考虑最省心的静态托管 + 轻量 API，而不是一上来迁复杂云函数链路。

## 为什么花了很久

### 1. 平台选择过早收敛

一开始把“国内访问”直接推向腾讯云，但没有先做横向对比：

- Vercel：海外访问方便，国内手机可能不稳定。
- Cloudflare Pages：部署体验好，但国内网络不一定稳定。
- Netlify：类似 Vercel，国内访问仍有不确定性。
- 腾讯云 CloudBase：国内访问更好，但配置和费用细节更多。
- 阿里云/华为云：也可选，但需要同样做探针验证。

教训：平台不是靠直觉选，应该用最小探针验证。

### 2. 没有先做最小可部署探针

正确做法应该是先部署一个极小项目：

```text
GET /
GET /health
GET /static/style.css
POST /api/echo
```

并验证：

- PC 能打开
- 手机流量能打开
- 静态资源不会变成下载
- API 能返回 JSON
- 环境变量能读取
- 费用模型明确

这些都通过后，再迁真实站点。

### 3. 项目形态已经复杂

真实项目不是纯静态页，它包含：

- 前端 HTML/CSS/JS
- Express 服务
- DeepSeek API
- 访问码逻辑
- Vercel 残留结构
- 腾讯云部署结构
- 本地 public 目录和根目录重复文件

这种项目迁移时最容易出现入口冲突、路径冲突和静态资源错配。

### 4. 腾讯云入口约定和直觉不一致

平台文档会告诉你支持 Node/Express，但具体到部署链路时，入口文件、根目录、构建目录、服务端口、静态资源目录都可能有平台约定。

如果前端也叫 `app.js`，后端也需要 `app.js`，就可能出现平台把浏览器端 JS 当后端入口执行的问题。

### 5. 费用风险没有提前讲清楚

这是最需要复盘的地方。

哪怕只是小网站，只要创建云函数、云托管、构建、公网流量、日志等资源，都可能产生费用或欠费。以后任何云资源操作前都要先说清：

- 是否免费
- 免费额度是什么
- 超出后怎么计费
- 如何停止服务
- 如何删除资源
- 预计一个月成本是多少

## 下次部署流程

### Step 1：先问清目标

- 是作品集公开展示，还是只给对象看？
- 是否需要 AI？
- 是否需要访问码？
- 是否必须国内手机流量可访问？
- 可接受月成本是多少？

### Step 2：做平台探针

每个平台先部署最小项目，不碰真实项目。

探针通过标准：

- 首页 200
- CSS/JS 200 且 MIME 正确
- `/health` 200
- 手机流量可访问
- 环境变量可用
- 控制台能看到费用和停止方式

### Step 3：迁移真实项目

迁移时先拆清楚：

```text
server/
  app.js
public/
  index.html
  client.js
  style.css
```

不要让后端入口和前端脚本重名。

### Step 4：上线后回测

固定检查：

- 首页
- 静态资源
- 推荐 API
- AI API
- 手机访问
- 日志
- 费用面板

## 可复用经验

- 不要把“官方支持”理解为“当前项目低风险”。
- 不要在未确认费用时创建云资源。
- 不要直接迁完整项目，先做探针。
- 不要把真实 Key 放前端。
- 不要用静态 JS 暴露全量数据。
- 如果只是短期给少数人看，优先选简单、可关闭、可估价的托管方案。
